# Architecture and technical design

The Navigator interviews a staff member about one fictional administrative workflow and produces a decision brief for IT triage. A Python web service owns session state, question selection, suitability rules, governance and report generation. It serves a static browser interface and stores active sessions and approved reports in a dedicated SQLite database. A local model can select up to two relevant follow-ups from the approved question bank and summarize the staff request when an analyst opens a completed assessment.

```text
Browser → Navigator HTTP → interview rules → SQLite
                         ↘ local model → allowed follow-up question ID
Review → deterministic assessment → Markdown download
Analyst detail → local model → short request summary → SQLite
```

Docker Compose publishes the application on Mac mini loopback port 8878 under project `flagcity-navigator`. The model runs on Apple Silicon using Metal at loopback port 8879 and has its own weights, runtime and launch script. The app reaches the model through Docker Desktop's host bridge. The MacBook can use the same app and model without Docker for a Wi-Fi-off demonstration. The hosted demo has a distinct HTTPS hostname routed through the Mac mini’s existing Cloudflare connector. The MacBook uses loopback for both services and needs no internet runtime access. The old application's directory, containers, network, model, database and port are outside this design.

The question bank is versioned structured input. Session actions replay the ordered transcript through the server's next-question function. Back removes the final answer and recomputes the remaining path. The interview and Review explain that editing an earlier answer clears its dependent answers. Model choices are constrained and recorded only for the answer that triggered them. A session revision and SQLite transaction prevent stale responses overwriting newer answers. The app saves the assessment and Markdown when staff confirm. Earlier downloads can use the current handoff layout with the original recorded decisions and answers. The demo uses unguessable session IDs stored in each browser tab, no user directory or global browsing endpoint, and loopback by default. The deployed app explicitly allows the public hostname and matches a browser’s HTTPS origin against it.

The interview checks clearance to conclude after each answer. Goal, current process and existing capability come first. Data, systems, access, impact, ownership and decision boundary are required on every path. The existing-capability and live-decision paths end after those checks and any required human-oversight question. Unsettled rules or an unknown input or result can end with Further discovery. Routine new work can end after confirming stable rules, structured inputs, a predictable result, a single team, known tool status and a low-risk administrative scope. The review screen explains why the interview finished. The routing decision uses confirmed answer choices, and the written notes provide supporting context to read during triage.

A small, read-only change for one team in an approved workspace may fit Self-service even when it involves private staff information. The assessment puts that proposal on hold for IT to confirm who may see the data, where it may be used and whether the proposed use is allowed. Potential criminal justice or patient data remains outside that self-service route.

For the opening answer, the local model identifies short excerpts for the start, steps and finish of the current task. The opening response is limited to 900 characters. The server removes email-like text, screens out proposal language, checks that excerpts occur in the answer, and uses a fixed question based on the missing details. If all three are present, the interview proceeds to the existing-tool question. If the model is unavailable or returns unusable evidence, the interview asks the standard workflow question. The saved assessment identifies excerpts from the opening answer. Revising that answer recalculates the evidence before the next question.

Every written answer is also screened for details relevant to unanswered topics. Rules match explicit language and keep the original sentence with its source answer. Later questions can show that sentence so staff can confirm a choice or include it without retyping. A clear example with both a sample input and an expected result can satisfy the optional example question, and Review and the export identify where it came from. All six required governance checks and any applicable human-oversight question still require a staff choice. Unrecognized wording follows the regular interview, and replay after an edit drops context from any answers that were cleared. This screening works with the local model turned off.

Staff see a short, optional writing field alongside choice-based questions. The question-specific label and example show what extra detail would help IT. “Why are we asking?” explains how each answer informs the assessment and stays collapsed until a staff member opens it. A choice is sufficient on choice-based questions, and the first workflow description requires a written answer. The required checks use plain-language prompts and explicitly invite “I’m not sure.” Uncertainty on any of the six mandatory checks goes to IT for review.

The analyst view reads finalized reports from the existing database. It adds a single local analyst account and expiring, revocable sessions stored by token hash. An optional staff estimate records the expected benefit at review without changing the interview count or recommendation. Consequence is the reported impact if the result is wrong. Indicative delivery effort is based on integration, permissions and the number of affected teams, and is shown separately from risk and governance. The dashboard supports filters, cross-tabulation, read-only report access and CSV. It leaves older reports intact and treats missing benefit as unestimated. A new custom intake collects a name and email. The app stores them in a separate SQLite contact table, alongside the intake but outside the model request, analytics and report exports. A submitted assessment receives a participant receipt with a copyable reference ID. The signed-in analyst can find that ID, review the saved record and draft a follow-up in their mail app. Review status is separate from the governance decision.

See the project brief for suitability, risk, IT routing and policy boundaries, and the operations guide for installation and testing.

**Request at a glance** loads a short excerpt of the confirmed intake goal immediately. The signed-in browser then requests a summary if none is saved. The existing local model receives up to 300 characters each from the goal and desired result, with email-like text removed. The app uses confirmed choices to describe any tool connection or human approval and stores successful model text in a separate analyst-only field in the saved interview. The server rules continue to own solution fit, risk, IT involvement, holds and exports. Reopening uses the saved summary. If inference fails, the goal excerpt stays visible and a later open can retry.
